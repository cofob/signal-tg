# План: перевод Telegram Web A на Signal

Статус: согласован 2026-11-20, решения в разделе 9. Название продукта: TeleSignal.

Цель: веб-клиент на кодовой базе Telegram Web A (Teact, `src/global`, компоненты), который работает как связанное устройство Signal (как Signal Desktop) и поддерживает функции Signal, доступные связанному устройству. Вся клиентская логика и криптография выполняются в браузере: libsignal собирается в WebAssembly. Прокси нужен только для сетевого доступа к серверам Signal. Функции Telegram без аналога в Signal удаляются.

Эталоны: Signal Android задаёт поведение и лимиты; Signal Desktop показывает, что умеет связанное устройство, и служит главным источником кода для переноса, потому что написан на TypeScript.

## Ход работ

Этап 0, сделано (2026-11-20):

- `rust/libsignal/`: крейты libsignal v0.108.3; `rust/signal-wasm/`: WASM-мост протокола (имена функций как у `Native`) и TLS-клиент на rustls. Сборка: `npm run signal:wasm`, результат в `src/lib/signal/wasm/generated`.
- `proxy/`: туннель WebSocket -> TCP на Rust (проверка ClientHello и SNI, лимиты на клиента, баны), `npm run signal:proxy`; политика без привязки к транспорту в `proxy/src/lib.rs` для Tauri.
- protobuf-es: `npm run signal:proto` (`buf generate`), схемы в `src/lib/signal/proto/schema`, код в `src/lib/signal/proto/generated`.
- `src/lib/signal/net`: TLS через туннель, HTTP/2 с откатом на HTTP/1.1, WebSocket, протокол `WebSocketResources`.
- `src/lib/signal/account`, `receiver`, `chat`, `store`, `sender`: привязка устройства, загрузка prekeys, чат-сокет, расшифровка конвертов, хранилище в IndexedDB, отправка с обработкой 409/410 и запросы синхронизации после привязки.

Этап 2, начат: движок умеет скачивать и расшифровывать вложения, разбирать синхронизацию контактов, читать и записывать storage service, получать профили и состояние групп v2 (zkgroup в WASM). `SignalClient` держит соединения и делает протокольную работу без UI:

- Отправка через sealed sender по неаутентифицированному сокету. Сертификат запрашивается без номера, ключи доступа берутся из ключей профилей. На 401 отправка идёт с идентификацией.
- Отправка в группы через sender keys: одно сообщение multi-recipient sealed sender с `Group-Send-Token` из group send endorsements, которые приходят с состоянием группы. SKDM уходит 1:1 устройствам без нашего ключа; ключ меняется после удаления участника и раз в 14 дней. Участникам без endorsements, группам меньше трёх человек и при отказе сервера (401, 403, 404) сообщение уходит каждому отдельно. Расшифровка сообщений с ключом отправителя и обработка SKDM работают.
- Квитанции (доставка, прочтение, просмотр), индикатор набора, синхронизация прочтения и просмотра, копия отправленного (`Sent`) для своих устройств.
- Повторные запросы: при ошибке расшифровки отправителю уходит `DecryptionErrorMessage`. На чужой запрос сессия архивируется, сообщение пересылается из журнала отправленного (сутки), в группах вместе с SKDM. Без сообщения в журнале участник группы получает SKDM, иначе после архивации сессии уходит null message.
- Расшифрованный текст сохраняется в `unprocessed` до обработки. Операции протокола идут по одной (`SignalStore.runExclusive`), чтобы шифрование и расшифровка не затирали состояние сессии.
- При подключении обновляются capabilities устройства.
- Локальная база `MessageDb` (IndexedDB: беседы и сообщения, индексы по беседе, по автору со временем и по сроку исчезновения). Id сообщений растут в порядке прихода, как сортирует Signal Desktop.
- `MessageProcessor` разбирает входящее в базу: сообщения 1:1 и групп, правки с историей, реакции, удаление автором и админом, опросы (голоса, закрытие), закреплённые сообщения, таймеры исчезновения с версиями (таймер беседы 1:1 уходит сообщением с `EXPIRATION_TIMER_UPDATE` и растущей версией). Из синхронизации он берёт отправленное с других устройств, прочтение, просмотр, просмотр view-once, контакты, блокировки, настройки и ответы на запросы переписки. Ещё он обрабатывает квитанции на свои сообщения и индикатор набора. Квитанции доставки уходят пачками. Прочтение запускает таймеры и отправляет квитанции прочтения (если включены) и синхронизацию. Исчезнувшие сообщения удаляются по таймеру. Он же отправляет свои сообщения со статусами по получателям. Профили новых бесед загружаются по одному.
- Запросы на переписку (как `ts/util/isConversationAccepted.preload.ts` в Desktop): беседа принята, если это Note to Self, мы её приняли, писали в неё или storage service отмечает её `whitelisted`, собеседник есть в контактах телефона или в личной беседе нет сообщений. Кто добавил нас в группу, мы не знаем, поэтому группа остаётся запросом, пока её не примут. В запросы не уходят квитанции прочтения и просмотра, набор и наш ключ профиля. Ответы ACCEPT, DELETE, BLOCK и SPAM применяются локально и уходят синхронизацией `messageRequestResponse`; принятие отправляет собеседнику ключ профиля, жалоба идёт на `POST /v1/messages/report/{aci}/{serverGuid}` с последними тремя сообщениями и `reportSpamToken` последнего конверта. В интерфейсе под заголовком запроса стоит плашка `ChatReportPane` с кнопками «Принять», «Удалить», «Заблокировать» и (для личных бесед) «Пожаловаться»; поле ввода остаётся, и отправка сообщения принимает запрос. Выйти из группы при блокировке или удалении, как Desktop, пока нельзя.
- Блокировки: всё от заблокированного отправителя и из заблокированной группы отбрасывается без квитанций. Блокировки приходят из sync `blocked` (номера без ACI сохраняются отдельно) и storage service. Смена блокировки уходит в storage service, а основному устройству, как в Desktop, ещё и полный список sync `blocked` (основное устройство заменяет им свой список) вместе с `messageRequestResponse`. Экран «Заблокированные» в настройках показывает заблокированные контакты и группы.
- Storage service в обе стороны (`src/lib/signal/storage`, как `ts/services/storage.preload.ts` в Desktop). Синхронизация берёт манифест новее сохранённого (`GET /v1/storage/manifest/version/{n}`), скачивает только новые для устройства записи и сливает их: контакты, группы, архив, mute, «непрочитанное», блокировки, `whitelisted`, Note to Self, закреплённые беседы, настройки квитанций, набора и превью ссылок. Манифест и расшифрованные записи хранятся в `SignalStore` целиком, с полями, которых клиент не знает, и с записями других типов (истории, папки, стикеры, ссылки на звонки). Локальные изменения архива, закрепа, mute, «непрочитанного», блокировки и принятия запроса (через `MessageProcessor`) помечают поля записей в `storageChanges`; синхронизация через 500 мс (без соединения — после подключения) пишет их поверх последнего манифеста: версия + 1, изменённые записи под новыми случайными id (старые удаляются), прочие поля и неизвестные поля остаются, ключи записей из `recordIkm` манифеста (без него — ключи `Item_<id>`). Беседа без записи получает новую при первом изменении; запись аккаунта (имя, фамилия и путь аватара пишутся при записи профиля) создаёт только основное устройство. Основное устройство без манифеста создаёт его (версия 1: запись аккаунта и записи принятых или заблокированных контактов и групп под новым `recordIkm`), а манифест, который не расшифровывается его ключом, заменяет новым с `clearAll`; связанное устройство в этом случае только сообщает об ошибке. Связанное устройство принимает ключ профиля из записи аккаунта (его меняет основное устройство) и перезапрашивает свой профиль; ключ профиля контакта из записи заменяет локальный только при первой синхронизации или без локального ключа, иначе локальный ключ помечается к записи. Запись очищает только изменения записей, которые вошли в неё. При 409 манифест читается заново: удалённые значения побеждают в полях, которые здесь не менялись, локальные — в изменённых; после трёх конфликтов подряд синхронизация сдаётся. После записи другим устройствам уходит `fetchLatest` (`STORAGE_MANIFEST`), входящий `fetchLatest` запускает синхронизацию. Закреп ограничен четырьмя беседами при закреплении; закрепы бесед, которых здесь нет (например, release notes), сохраняются в конце списка.
- `deleteForMe` (`ts/util/deleteForMe.preload.ts` в Desktop): входящие удаления сообщений, бесед (до самого нового из названных сообщений, при `isFullDelete` и без адресуемых сообщений целиком), локальных бесед и вложений (по `clientUuid` или `digest`); удаление для себя и удаление беседы отсюда отправляют такую же синхронизацию. Удаление отдельного вложения отсюда не отправляется: в интерфейсе его нет.
- Группы v2 (`src/lib/signal/groups/`, по Signal Desktop `ts/groups.preload.ts`): создание (`PUT /v2/groups/`) и изменения (`PATCH /v2/groups/` с presentation учётных данных; после 409 состояние запрашивается заново и изменение строится снова): название, описание, аватар (шифруется и загружается на CDN 0 по форме `/v2/groups/avatar/form`), таймер, участники (с expiring profile key credential из `/v1/profile/{aci}/{version}/{request}`, без него приглашение), удаление с баном, разбан, админы, права на изменение и добавление, «только админы пишут», ссылка `https://signal.group/#...` (включение с одобрением и без, сброс, выключение), заявки, вступление по ссылке, принятие и отказ от приглашения, выход. Своё изменение применяется локально, endorsements берутся из ответа, участникам, приглашённым и удалённым уходит `groupV2` с подписанным `groupChange`. Входящее изменение следующей ревизии применяется после проверки подписи сервера, пропущенные ревизии участник догоняет по журналу `/v2/groups/logs/`, остальные запрашивают состояние. Название ограничено 32 графемами, описание 480 (как в Android); правки названия, описания и аватара из одного сохранения уходят одним изменением; единственный админ не может выйти из группы с другими участниками, пока не назначит другого. Созданные группы и группы, в которые мы вступили, попросились или приняли приглашение, считаются принятыми. Изменения записываются в историю служебными сообщениями. Поля группы, которые не расшифровываются, очищаются, а такие пользователи пропускаются. Входящее групповое сообщение сначала доводит состояние группы до своей ревизии; его отбрасывают без квитанции, если нас или отправителя нет в группе или группа только для админов, а отправитель не админ, и группа, в которой нас нет, не создаёт беседу. Ответ 403 для группы, где мы были участником, сохраняет состояние без нас и заметку об удалении. Обновление группы уходит не срочным и повторяется для не получивших после следующего подключения. Названия и описания обрезаются по краям. Методы для UI: `src/api/signal/methods/groups.ts` (группы остаются basic groups без миграции в супергруппы).
- Загрузка вложений: шифрование с дополнением размера (`logPadSize`), форма `GET /v4/attachments/form/upload` и TUS-загрузка на CDN 3 одним запросом. Возобновления после обрыва и CDN 2 пока нет.
- Перенос истории при привязке (link and sync, `src/lib/signal/backups`): ссылка привязки объявляет `backup5`. Если телефон прислал `ephemeralBackupKey`, экран привязки показывает ход синхронизации, а устройство до подключения чат-сокета ждёт архив (`GET /v1/devices/transfer_archive`), скачивает его с CDN, проверяет MAC, расшифровывает, распаковывает и пачками пишет в `MessageDb`: аккаунт и настройки, контакты, группы из снимка, состояние бесед, сообщения с цитатами, реакциями, правками, вложениями (ссылки транзитного уровня), опросами и таймерами. Состояние переноса хранится в аккаунте, прерванный импорт продолжается. Вложения только из медиа-уровня бэкапа, звонки, истории, стикерпаки, платежи и большинство уведомлений групп не переносятся.
- Свой профиль (`profiles/writeProfile.ts`, как `ts/services/writeProfile.preload.ts` в Desktop; связанному устройству Desktop это разрешает): имя и фамилия, about и about emoji шифруются ключом профиля с дополнением до длин Desktop и уходят `PUT /v1/profile` с версией и commitment того же ключа. Новый аватар грузится формой S3 (`POST /` на `cdn.signal.org`, хост уже в `ALLOWED_HOSTS`), удаление шлёт `avatar: false`. Платёжный адрес и `phoneNumberSharing` берутся из текущего профиля и отправляются обратно без изменений. Остальным устройствам уходит `fetchLatest { LOCAL_PROFILE }`; входящий такой запрос перечитывает наш профиль. Ключ профиля не ротируется: это работа основного устройства. В интерфейсе «Изменить профиль» осталось имя, фамилия, about (эмодзи в начале текста становится about emoji), аватар с удалением и переход к юзернейму; день рождения, личный канал, покупка и список юзернеймов Telegram убраны.
- Юзернейм (`usernames/manageUsername.ts`, как `ts/services/username.preload.ts`): резерв кандидатов (`PUT /v1/accounts/username_hash/reserve`, хеши `Username_CandidatesFrom`/`Username_Hash`, свой номер через `Username_HashFromParts`), подтверждение с доказательством `Username_Proof` и новой ссылкой `UsernameLink_Create` (`PUT /v1/accounts/username_hash/confirm`), смена регистра без резерва с сохранением ссылки, удаление (`DELETE /v1/accounts/username_hash`), сброс и удаление ссылки (`PUT`/`DELETE /v1/accounts/username_link`). Ошибки libsignal несут имена `Native` (`NicknameTooShort` и т.д.). Экран «Имя пользователя» в настройках: поля ника и номера, резерв при вводе, ссылка `https://signal.me/#eu/...` с QR-кодом, копирование, сброс, удаление. Ссылки `signal.me/#eu/` и `#p/` (и `sgnl://signal.me/...` из Tauri) — deep links: юзернейм ищется без учётных данных и открывает чат, номер находит только известных собеседников (CDSI нет).
- Приватность номера (как Desktop с связанного устройства): «Кто видит мой номер» пишет зашифрованный `phoneNumberSharing` в профиль, «Кто может найти меня по номеру» — `PUT /v2/accounts/phone_number_discoverability`; показ номера всем включает поиск. Экран «Номер телефона» в приватности заменён на эти два выбора «Все»/«Никто». Текущие значения читаются из записи аккаунта storage service (`phoneNumberSharingMode`, `unlistedPhoneNumber`).
- Запись storage service для этих полей: изменения юзернейма, ссылки, показа и поиска номера помечаются полями записи аккаунта (`username`, `usernameLink`, `phoneNumberSharingMode`, `unlistedPhoneNumber` в `storageChanges`, `MessageProcessor.updateOwnAccount`) и уходят следующей записью storage service; пока они не записаны, чтение storage их не затирает. После записи нового юзернейма остальным устройствам уходит sync `usernameChange` (Desktop `getUsernameChangeSyncMessage`); входящий `usernameChange` перечитывает storage service.
- Safety numbers (`account/safetyNumber.ts`, как `generateSafetyNumber` в Desktop): `Fingerprint_New` версии 2 с ACI, 60 цифр блоками по пять и QR-код (`ScannableEncoding`, байтовый режим). В профиле собеседника пункт «Показать код безопасности» открывает окно с кодом, QR и «Отметить как проверенный»/«Снять отметку». Без ключа собеседника он берётся из профиля. Состояние проверки хранится в identity-записи (`Verified.State`), уходит sync `verified` и применяется из входящего (`processVerifiedMessage`: новый ключ сохраняется сразу с переданным состоянием). Смена ключа (`saveIdentity` в `store/protocolStores.ts`, общий путь для расшифровки, prekey bundle и ключа из профиля) переводит проверенный контакт в `UNVERIFIED` и через `SignalStore.onIdentityChange` добавляет уведомление «Ваш код безопасности с X изменился» в личный чат и общие группы; отметки проверки тоже показываются уведомлениями. Отправка проверенному контакту с новым ключом один раз падает с `UntrustedIdentity`, ключ сохраняется непроверенным, следующая отправка идёт. Отличие от Desktop: `UNVERIFIED` не блокирует отправку до подтверждения пользователем (окна «Отправить всё равно» нет), сессии других устройств контакта при смене ключа не архивируются, ключ отправителя групп не сбрасывается.
- Регистрация нового аккаунта по номеру телефона, браузер становится основным устройством (device 1). Движок (`src/lib/signal/account/register.ts`, запросы как в libsignal-net `rust/net/chat/src/ws/registration` и Desktop `standaloneInstaller`): сессия `POST /v1/verification/session` без push-токена, captcha через `PATCH` (пользователь решает её на `signalcaptchas.org/registration/generate.html` в своей вкладке и вставляет ссылку `signalcaptcha://`; приложение эту страницу не загружает), код по SMS или звонку (`POST .../code` с `transport`, `client` и `Accept-Language`), проверка кода (`PUT .../code`), затем `POST /v1/registration` с basic auth `номер:пароль`, атрибутами аккаунта (registration ids, `fetchesMessages`, ключ доступа из нового profile key, `recoveryPassword` из нового AEP, capabilities, `discoverableByPhoneNumber`), identity-ключами и last-resort prekeys ACI и PNI, `skipDeviceTransfer`. После него: one-time prekeys (`PUT /v2/keys`), профиль с зашифрованным именем (`PUT /v1/profile`, `src/lib/signal/profiles/uploadProfile.ts`) и обычное подключение. До загрузки профиля аккаунт помечен `isRegistrationPending`, после перезагрузки регистрация продолжается с экрана имени. Ошибки: 429 с `Retry-After`, неверный код, истёкшая сессия, отказ captcha, 418/440 при отправке кода, 423 (registration lock: экран PIN, см. ниже), `pushChallenge` без captcha (браузер его пройти не может). Недоступный туннель даёт ошибку на экране: TLS-рукопожатие, на которое туннель не отвечает, прерывается через 20 с (`TlsTunnel`). WASM: `AccountEntropyPool_Generate`, `AccountEntropyPool_DeriveSvrKey` (им же storage service выводит master key), `SvrKey_DeriveRegistrationRecoveryPassword`, `SvrKey_DeriveRegistrationLock`. Основное устройство без связанных устройств не отправляет sync-сообщения (как Android); на `SyncMessage.request` пока не отвечает. - Поиск по номеру (CDSI, `src/lib/signal/cdsi/cdsiLookup.ts`, протокол libsignal-net `cdsi.rs`, которым пользуется Desktop `cdsLookup`): учётные данные `GET /v2/directory/auth` (кэш 23 ч, как в Desktop; сбрасывается вместе с лимитом при выходе из аккаунта), `/v1/{mrenclave}/discovery`, запрос с номерами, ACI и ключами доступа известных собеседников (без своего), токен, `token_ack`, ответ тройками (номер, PNI, ACI). - PIN и Registration Lock (SVR2, `src/lib/signal/svr/`). Выбор SVR2: им пользуются для PIN текущие Android (`SvrRepository`: только реализации SVR2, текущий и прошлый анклав) и Desktop (`restoreFromSVR2`, `storeWithSVR2`); SVR3 из клиентов убран, SVRB хранит forward secrecy бэкапов и PIN не защищает. PIN нормализуется как `PinHashUtil.normalize` (обрезка, цифры любых систем в ASCII, NFKD), хэш Argon2 с солью из имени пользователя SVR2 и группы анклава (`PinHash::make_salt`). Восстановление (`restoreMasterKey`, как `Svr2_RestoreMasterKey`): текущий анклав, при `MISSING` или 404 предыдущий; неверный PIN сообщает число оставшихся попыток, после последней данные удаляются. `MISSING` получается, только если анклав ответил; если оба анклава дали 404, не подключились или не прошли аттестацию, ошибка `unavailable` (попытка не тратится), и экран PIN остаётся с подсказкой: туннель должен пускать `svr2.signal.org` (прокси версий до этой не пускают), часы устройства должны быть верны. При ротации анклавов Signal MRENCLAVE в `src/lib/signal/config.ts` и Raft-конфигурации в vendored `attest` надо обновить вместе с libsignal, иначе восстановление даёт `unavailable`. Сохранение (`backupMasterKey`, как `Svr2_StartMasterKeyBackup`/`Svr2_FinishBackup`): сначала предыдущий анклав (404 пропускается), потом текущий, каждый backup и expose (expose повторяется до трёх раз), до 10 попыток. Регистрация на 423 (как Desktop `verifyPIN` и Android `restoreMasterKeyPreRegistration`): после экрана имени открывается экран PIN (`AuthPassword`), PIN с `svr2Credentials` из ответа 423 восстанавливает master key (повторная отправка, пока PIN проверяется, игнорируется; восстановленный ключ хранится до конца регистрации, поэтому повтор после сбоя регистрации попытку не тратит), аккаунт создаётся с `registrationLock` из `SvrKey_DeriveRegistrationLock` и `recoveryPassword` из этого master key; аккаунт хранит восстановленный `masterKey` вместо AEP, поэтому storage service старого аккаунта читается. Затем master key сохраняется в SVR2 заново со свежими `GET /v2/backup/auth` нового аккаунта (сбрасывает счётчик попыток, как `ResetSvrGuessCountJob`; три попытки, при неудаче уведомление предлагает сменить PIN в настройках). Без попыток или без `svr2Credentials` экран номера показывает, через сколько дней истечёт блокировка (`timeRemaining`). Настройки › Конфиденциальность › «Signal PIN» (только у основного устройства, `src/components/left/settings/SettingsSignalPin*.tsx`): создать или сменить PIN (`GET /v2/backup/auth`, запись в SVR2, capability `storage`), включить и выключить Registration Lock (`PUT`/`DELETE /v1/accounts/registration_lock`), выключить PIN (сначала блокировка, потом удаление из обоих анклавов). PIN не хранится, поэтому напоминаний PIN и переноса данных в новый анклав при ротации нет.

Фильтр по хостам (`signal.me`, `signal.group`, `signal.link`, `signal.tube`, `joingroup`, `addstickers`, `linkdevice`, `rereg`) остаётся в Rust, чтобы страница, открывающая `sgnl://`, не выводила окно вперёд; адреса ссылок в журнал не пишутся (номера и ключи групп).
  - Браузер: `navigator.registerProtocolHandler` принимает только схемы из белого списка или `web+…`, поэтому `sgnl` зарегистрировать нельзя. `web+sgnl` не регистрируется: ни один клиент Signal не создаёт такие ссылки, а браузер спрашивал бы разрешение ради ссылок, которых нет. Ссылки `https://signal.me`, `signal.group` и остальные снаружи приложения ведут на сайты Signal, откуда ОС передаёт `sgnl://` установленному приложению (Tauri). Страница принимает из `#?tgaddr=<адрес>` в адресе только ссылки Signal (`parseSignalLink`, затем `openSignalLink`; ссылки `tg:` и любые другие игнорируются, потому что адрес может подставить любая веб-страница), если понадобится обработчик `web+…`, шаблон — `/#?tgaddr=%s`. `tg://resolve?phone=` тоже ведёт к подтверждению (`PhoneNumberLookupModal`), а не к поиску в CDSI сразу.
- Голосовые: запись в поле ввода уходит вложением `audio/ogg` (Opus) с флагом `VOICE_MESSAGE`, длительностью и waveform; Desktop пишет MP3, Android и iOS AAC, воспроизведение OGG на iOS не проверено (риск в разделе 7).
- Истории (`src/lib/signal/stories`, `MessageProcessor`; по Desktop `MessageReceiver.#handleStoryMessage`, `ts/util/sendStoryMessage.preload.ts`, `ts/jobs/helpers/sendStory.preload.ts`, `ts/util/onStoryRecipientUpdate.preload.ts`, `ts/util/deleteStoryForEveryone.preload.ts`) лежат в отдельном хранилище `stories` базы `MessageDb` (версия 3) и удаляются через сутки после отправки. Приём: истории принятых контактов и групп, текстовые (текст, фон цветом или градиентом, стиль шрифта, цвета, превью ссылки) и с фото или видео (подпись с форматированием), `allowsReplies`; при выключенных историях, от заблокированных, от неучастников группы (по состоянию группы, которое загружается до обработки; если загрузка не удалась, история проходит, как сообщения) и просроченные отбрасываются; срок — сутки от меньшего из времени отправки и текущего по часам устройства, как в Desktop (часы отправителя не продлевают историю); копии историй с других устройств проверяются так же. С других устройств приходят копии отправленных историй (`Sent.storyMessage` со `storyMessageRecipients`), обновления получателей (`isRecipientUpdate`; история, которую больше никто не видит, удаляется), синхронизация просмотра; автор удаляет историю через `delete`. Просмотр (история показана, медиа загружено) отправляет синхронизацию и квитанцию просмотра, если включены квитанции просмотра историй (`storyViewReceiptsEnabled`; без значения — как квитанции прочтения) и автор не заблокирован. Ответ в личку — сообщение со `storyContext` (реакция — `reaction` со `storyContext`), он виден в чате; ответ на групповую историю уходит в группу как история (`story=true`) и хранится при истории, не в истории чата. Ответ привязывается к истории только своей беседы: ответ в группе — к истории этой группы, ответ в личке на нашу историю — от получателя с правом ответа. Квитанции просмотра своих историй и ответы на них дают списки «Кто видел» и ответов.
- Отправка историй: в My Story и свои списки рассылки из storage service (`StoryDistributionListRecord`: My Story со списком исключений или разрешённых, `allowsReplies`; получатели — только связи (принятые беседы и контакты телефона, не заблокированные); участники списка, известные только по PNI, не показываются и остаются в записи, пока аудитория не меняет смысл (исключения на включения или переход от списка людей к «все контакты»), а исключённый только по PNI человек, известный нам по ACI, получит историю, пока основное устройство не перепишет список; пока запись My Story не слита из storage service (после привязки, до первой синхронизации), отправка в My Story и запись его списка отказывают, умолчания «все контакты» нет), в группы. История, не дошедшая ни до кого (в том числе в одну из групп при доставке в My Story), не хранится; ответ в группу, не дошедший ни до кого, возвращает ошибку и не сохраняется при истории. Списки получают одну историю с одной меткой времени, каждый человек — один раз, отвечать может, если это разрешает хотя бы один его список. Шифрование sender key, distribution id списка — его id; отправка multi-recipient `story=true` без ключей доступа и `Group-Send-Token`, SKDM списков тоже уходят как истории; меньше двух получателей — 1:1 sealed sender `story=true` без ключа доступа. Затем `Sent` со `storyMessageRecipients`. Удаление для всех: групповой истории — `delete` в группу, истории списка — `delete` каждому получателю (`story=true`) и `isRecipientUpdate` без списков; история удаляется локально после отправки, при ошибке остаётся (интерфейс сообщает об ошибке и о частичной доставке), без соединения удаление ждёт подключения; медиа истории стирается из кэша вложений.
- Storage service для историй: `hideStory` контактов и групп, `storiesDisabled` и `storyViewReceiptsEnabled` записи аккаунта, списки рассылки читаются и записываются (новый список, изменения целиком, удаление с `deletedAtTimestamp`; участники не ACI, например PNI, сохраняются как есть; My Story записывается с именем-идентификатором, как Desktop). После обновления сохранённые записи один раз сливаются заново (`STORAGE_MERGE_PASSES`: списки и поля историй), локальные изменения побеждают; выключение историй на другом устройстве стирает сохранённые истории.
- Пока нет: звонки, ранние квитанции, пришедшие до копии отправленного; в группах: метки участников, завершение группы, приглашения по PNI в UI. В историях: превью ссылок в своих текстовых историях, перекодирование видео до 30 с, ответы вложениями и голосом, `storySendMode` групп, историй-онбординга.

Интерфейс работает на движке через провайдер `src/api/signal` вместо GramJS: воркер вызывает методы с теми же именами и сигнатурами (`methods/index.ts`: список чатов, история, отправка, медиа, профили, настройки, управление группами), а изменения `MessageDb` превращаются в обновления приложения (`updaters/`). ## 1. Проверенные факты

Источники: клоны Signal-Android, Signal-Desktop, libsignal, RingRTC (2026-11-20), проверки сборки и сети из этого окружения.

1. **libsignal собирается под `wasm32-unknown-unknown`** (`cargo check`, Rust 1.98.1 из `rust-toolchain` libsignal). Нужны только фича `wasm_js` у `getrandom` 0.2/0.3/0.4 и `protoc` для сборки `spqr`. Собираются крейты: `libsignal-core`, `signal-crypto`, `libsignal-protocol` (PQXDH, Double Ratchet, SPQR, sealed sender, sender keys), `zkgroup` (группы v2, учётные данные профиля), `usernames`, `libsignal-account-keys`, `libsignal-message-backup` (перенос истории).
2. **`attest` не собирается под wasm32 с BoringSSL**: он зависит от `boring-signal`, который использует для X.509, ECDSA P-256, BigNum и ASN.1 при проверке SGX DCAP (около 70 вызовов в 4205 строках `src/dcap*`, `src/cert_chain.rs`). `attest` нужен для CDSI (поиск по номеру) и SVR2 (PIN). Решено подменой `boring` на `rust/boring-shim` (чистый Rust) через `[patch]` в `rust/signal-wasm/Cargo.toml`.
3. **В libsignal нет WASM-моста.** Мосты генерируются макросами `rust/bridge/shared/macros` (433 функции `bridge_fn`) для FFI, JNI и Node. Node-мост занимает 5788 строк (`rust/bridge/shared/types/src/node`). Обёртка `@signalapp/libsignal-client` на TypeScript (`node/ts`, 19 608 строк с тестами и `net`) обращается к нативному модулю только через объект `Native`.
4. **Все хосты Signal отдают сертификат частного CA «Signal Messenger, LLC»**: chat, storage, cdn, cdn2, cdn3, cdsi, sfu.voip (проверено `openssl s_client`). Браузер отвергнет такой TLS независимо от CORS. Desktop закрепляет этот CA (`config/default.json`, `certificateAuthority`). Значит, прокси обязателен.
5. **Звонки Signal несовместимы с WebRTC браузера.** RingRTC начиная с V3 отключает DTLS и задаёт ключи SRTP через собственный обмен Диффи-Хеллмана (`ringrtc/src/rust/src/core/connection.rs:773`, `signaling.rs:26`). WebRTC браузера требует DTLS-SRTP и не даёт задать ключи SRTP.
6. **Протокольный слой Signal Desktop** (`ts/textsecure/`) занимает 22 209 строк, импорт бэкапа (`ts/services/backups/import.preload.ts`) 4842 строки. Это основной код для переноса.
7. **Связанное устройство** получает при привязке `ProvisionMessage`: ключи ACI и PNI, profile key, `ephemeralBackupKey`, `accountEntropyPool`, `mediaRootBackupKey`. После привязки Desktop отправляет `PUT /v1/devices/link`, запрашивает синхронизацию CONTACTS, CONFIGURATION и BLOCKED, при наличии ключа скачивает архив истории (`v1/devices/transfer_archive`), затем синхронизирует storage service (`ts/background.preload.ts:1940-2000`). На запросы синхронизации отвечает только основное устройство.
8. **Только основное устройство** может: менять discoverability и атрибуты аккаунта, PIN и registration lock, ротировать profile key, менять номер, удалять аккаунт, управлять бэкапами и связанными устройствами (`util/assembleAccountAttributes.preload.ts:17` в Desktop).
9. **Порядок и идентификаторы в Signal Android:** сообщения сортируются по `DATE_RECEIVED` (`MessageTable.getConversation`), получатели адресуются локальным числовым `RecipientId` (`core/util/.../RecipientId.kt`), правки хранятся отдельными ревизиями (`LATEST_REVISION_ID`).
10. **Telegram Web A завязан на числовые id:**
    - `isUserId` проверяет префикс `-` (96 мест в 66 файлах); `isChannelId` и `getRawPeerId` разбирают id через `BigInt`.
    - Цвет аватара считается как `getPeerIdDividend(id) % 7`.
    - Ключ сообщения разбирается регуляркой `/^msg(-?\d+)-(\d+)/`.
    - `viewportIds`, `listedIds` и `lastReadInboxMessageId` являются `number[]` или `number`, сравниваются численно, история пагинируется по offsetId.
    - Локальные сообщения имеют дробный id.
11. **Объём GramJS и API Telegram:** `src/lib/gramjs` занимает 48,5 тыс. строк, `src/api/gramjs` 33,9 тыс. Наружу торчат около 574 методов, из `src/global` вызываются около 518. Объединение `ApiUpdate` содержит 150 типов. Транспортно-нейтральные типы `src/api/types` (6,4 тыс. строк) сохраняются.
12. Signal Desktop записывает голосовые в MP3 (`ts/workers/mp3Encoder.std.ts`), Telegram Web A в OGG/Opus (`opus-recorder`). Не проверено, воспроизводит ли Signal iOS OGG/Opus.
13. **Key transparency в браузере возможна, но требует переноса клиента.** Проверка доказательств лежит в крейте `libsignal-keytrans` (около 3,5 тыс. строк; `curve25519-dalek`, `ed25519-dalek`, `prost`, `sha2`, `hmac`, без ввода-вывода) и собирается под wasm32 как остальные. Протокол клиента (`check`: обновление distinguished tree head раз в две недели, выбор search или monitor, слияние `AccountData`, около 3,3 тыс. строк в `rust/net/chat/src/api/keytrans*`) живёт в `libsignal-net-chat`, который тянет tokio, tonic и `libsignal-net` и под wasm32 не собирается. Транспорт ему нужен узкий: трейт с тремя запросами на неаутентифицированном сокете, `POST /v1/key-transparency/search`, `GET /v1/key-transparency/distinguished?lastTreeHeadSize=`, `POST /v1/key-transparency/monitor` (JSON с protobuf в `serializedResponse`, `rust/net/chat/src/ws/keytrans.rs`). Нужно: завендорить `rust/keytrans`; перенести в `rust/signal-wasm` модули `api/keytrans`, `monitor_and_search`, `verify_ext`, `maybe_partial` с транспортом через JS-колбэки, как хранилища в `stores.rs`, и экспортом `KeyTransparency_Check` с сигнатурой `Native`; взять боевые ключи подписи, VRF и аудиторов из `KEYTRANS_CONFIG_PROD` (`rust/net/src/env.rs`); хранить `AccountData` по контактам и distinguished tree head (как `KeyTransparencyStore` в Desktop); передавать ACI с identity key, номер с ключом доступа (если номер известен) и хеш юзернейма; показать в окне кода безопасности состояния Desktop (`idle`, `running`, `ok`, `fail`, `unavailable`) и сделать самопроверку. Desktop включает это удалённым конфигом. В этой работе не сделано.

## 2. Архитектура

```
Браузер
  UI: src/components, src/global          сохраняем, вычищаем Telegram-функции
  src/api/signal/   (Worker мастер-вкладки, вместо src/api/gramjs)
      methods/      реализации Methods поверх локальной БД и движка
      updates/      входящие события -> ApiUpdate
  src/lib/signal/   (вместо src/lib/gramjs)
      wasm/         libsignal в WASM + TS-обёртка из libsignal/node/ts
      proto/        TS-кодеки, сгенерированные из .proto Signal Android
      net/          REST и WebSocket Signal (порт WebAPI, SocketManager, WebsocketResources)
      protocol/     приём и отправка (порт MessageReceiver, SendMessage, OutgoingMessage)
      provisioning/ groups/ storage/ cds/ attachments/ backups/ profiles/ stickers/
      store/        IndexedDB: ключи, сессии, prekeys, sender keys, получатели,
                    чаты, сообщения, необработанные конверты, вложения
        |
        | HTTPS + WSS на свой origin
        v
proxy/  (Rust, без состояния на диске)
  WebSocket -> TCP туннель к хостам из allowlist, TLS не расшифровывает,
  проверяет SNI в ClientHello, ограничивает клиентов
        |
        v
Серверы Signal (chat, storage, cdn0/2/3, cdsi, svr2)
```

Решения:

- **Архитектура повторяет Telegram Web A.** GramJS живёт в Worker мастер-вкладки и отдаёт `ApiUpdate`; на его место встаёт движок Signal. Мастер-вкладка держит единственный WebSocket устройства, другие вкладки ходят через неё (`src/util/browser/multitab.ts`).
- **WASM-мост.** Нужные крейты libsignal v0.108.3 лежат в `rust/libsignal/` без изменений, кроме перечисленных в `rust/libsignal/NOTICE.md`. Собственный крейт `rust/signal-wasm/` (wasm-bindgen) экспортирует функции с именами и сигнатурами `Native` из `libsignal/node/ts/Native.ts`, только нужное подмножество. Движок вызывает их напрямую через `src/lib/signal/wasm`; обёртку `node/ts` переносить не стали: прямые вызовы короче, а совпадение имён с `Native` упрощает перенос кода Desktop. `libsignal-net` в сборку не входит: сеть написана на TypeScript поверх туннеля.
- **CDSI и SVR2** работают через `attest` в WASM: BoringSSL заменяет `rust/boring-shim` (чистый Rust на `asn1`, `p256`, `sha2`), сам `attest` не патчится, кроме `time_t`. Поиск по юзернейму CDSI не нужен.
- **Protobuf:** [protobuf-es](https://github.com/bufbuild/protobuf-es) (`@bufbuild/protobuf`), код генерирует `buf generate` по `buf.gen.yaml` (`npm run signal:proto`). `.proto` копируются из Signal Android с указанием версии. 64-битные числа приходят как `bigint`, неизвестные поля сохраняются (нужно storage service).
- **Хранилище:** IndexedDB без новых зависимостей. Сырой конверт сначала сохраняется в `unprocessed`, потом подтверждается серверу (как в Desktop), поэтому сбой вкладки не теряет сообщения. Вызывается `navigator.storage.persist()`. При заданном код-пароле ключи и история шифруются (расширяем `src/util/passcode`).
- **Идентификаторы как в Signal Android:** движок выдаёт локальные числовые id. Пользователь: положительное целое, группа: отрицательное целое. ACI, PNI, номер и groupId хранятся полями. Сообщения нумеруются целыми числами внутри чата в порядке получения. Identity сообщения в Signal: `(чат, ACI автора, sentTimestamp)`, уникальный индекс. Цитаты, реакции, правки, удаления, квитанции, голоса и закрепления находят сообщение по нему. Правка сохраняет id и пишет ревизию. Так `isUserId`, ключи сообщений, viewport и пагинация работают без переписывания.
- **Лицензии:** libsignal и Signal Desktop распространяются под AGPLv3, Telegram Web A и Signal Android под GPLv3. GPLv3 §13 разрешает такое объединение; перенесённые и встроенные AGPL-части сохраняют свою лицензию. Исходники публичны, требование AGPL о раскрытии кода выполняется. Добавляем NOTICE с перечнем.

### Режим прокси

| | P1: HTTP/WS reverse proxy | P2: TCP-туннель, TLS в WASM |
| --- | --- | --- |
| Что делает прокси | Завершает TLS к Signal, проверяет закреплённый CA, добавляет CORS, переносит заголовки авторизации для WebSocket | Пересылает байты WebSocket в TCP-соединение с хостом из allowlist |
| Что видит прокси | Учётные данные устройства (`aci.deviceId:password`), пути запросов (чьи prekeys, какие вложения), зашифрованные E2E конверты | Только имена хостов и объём трафика |
| Работа в браузере | `fetch` и `WebSocket` | TLS (rustls) в WASM, свои клиенты HTTP/2, HTTP/1.1 и WebSocket поверх него |
| Размер прокси | 200–300 строк | ~100 строк |
| Риск | Злоумышленный прокси может вызывать API от имени устройства, но не прочитает и не подделает сообщения без ключей | Сложнее, медленнее на больших вложениях |

Выбран P2. TLS делает rustls внутри `rust/signal-wasm` в sans-IO режиме: TypeScript передаёт байты между туннелем и TLS-сессией. Для хостов Signal доверяем только закреплённому CA Signal. Поверх TLS работают свои клиенты HTTP/2 (ALPN `h2`, одно соединение на хост), HTTP/1.1 и WebSocket, поэтому заголовки авторизации WebSocket задаём сами.

Адрес туннеля по умолчанию задаёт сборка (`SIGNAL_TUNNEL_URL`, иначе `/tunnel` своего origin). Пользователь меняет его настройкой «Прокси-сервер» (раздел «Данные и память» или кнопка на экране привязки, `SharedSettings.signalProxyUrl`): допускаются `wss://` и `ws://` для localhost, после сохранения API переподключается через новый туннель.

## 2a. Аккаунты без номера телефона

Signal позволяет аккаунты без номера: у них нет PNI и номера, собеседники находят их по юзернейму. Поддержка есть в выпущенной libsignal v0.108.3 (`AuthCredentialWithPniResponse::receive_without_pni`, поле `ProvisionMessage.authCredentialSalt`) и в Signal Desktop (capability `nopni2`, «e164-less linking», `ts/textsecure/Provisioner.preload.ts`, `ts/services/groupCredentialFetcher.preload.ts`). В main libsignal после v0.108.3 два коммита, к этому не относящихся.

Сделано:

- QR-ссылка объявляет `nopni` и `nopni2`.
- Привязка без PNI: требуется `authCredentialSalt`, PNI-ключи и `pniRegistrationId` не создаются, capability `optionalPhoneNumber` равна `true`; соль хранится в аккаунте.
- Групповые auth credentials без PNI: `ServerPublicParams_ReceiveAuthCredentialZkcWithoutPni` с солью, дальше та же zk-презентация.
- Конверты на PNI для такого аккаунта отклоняются, всё адресуется ACI.
- Сертификат sealed sender запрашивается без номера (`?includeE164=false`) для всех аккаунтов; при подключении capabilities устройства обновляются с `optionalPhoneNumber`.
- Поиск собеседников по юзернейму и по ссылке `signal.me/#eu/...` без учётных данных (`Username_Hash`, `UsernameLink_DecryptUsername` в WASM). Проверено на настоящем сервере: неизвестные имя и ссылка дают «не найдено».

Осталось (вместе с соответствующими функциями):

- UI: не показывать и не требовать номер в профиле и экранах привязки (настройки приватности номера сделаны).

Не проверено на живом аккаунте без номера: нужен такой аккаунт на телефоне.

## 5. Этапы

Этапы 0 и 1 идут параллельно: этап 0 пишет `src/lib/signal`, `proxy/` и форк libsignal, этап 1 удаляет код из `src/components`, `src/global` и `src/api/gramjs`.

### Этап 0. Спайки, снимающие риски

1. **libsignal в WASM.** Форк libsignal, цель `wasm` в макросах моста, сборка через wasm-bindgen, `node/ts` поверх WASM. Готово, когда в браузере две пары хранилищ проводят сессию PQXDH, шифруют и расшифровывают сообщение, sealed sender и sender key работают, размер `.wasm` измерен.
2. **Прокси-туннель и TLS в WASM.** Туннель WebSocket -> TCP с allowlist (chat, storage, cdn0/2/3, cdsi, contentproxy), rustls в WASM с закреплённым CA Signal, клиенты HTTP/1.1 и WebSocket на TypeScript. Готово, когда браузер открывает `wss://chat.signal.org/v1/websocket/provisioning/` через туннель.
3. **Protobuf** (`npm run signal:proto`): `SignalService`, `Provisioning`, `WebSocketResources`, `Groups`, `DecryptedGroups`, `StorageService`, `Backup`.
4. **Привязка и первое сообщение.** QR в браузере, скан с Android, расшифровка `ProvisionMessage`, `PUT /v1/devices/link`, загрузка prekeys, WebSocket, расшифровка входящего конверта. Готово, когда текст с телефона виден в консоли.

### Этап 1. Вырезать функции Telegram, пока бэкенд Telegram ещё работает

Удаляем по одной области за коммит из раздела 4: компоненты, действия, редьюсеры, селекторы, методы `src/api/gramjs/methods`, типы `src/api/types`, члены `ApiUpdate`, ключи локализации, записи реестров настроек и горячих клавиш, миграции кэша. Приложение остаётся рабочим на Telegram, поэтому регрессии видны в браузере.

Готово, когда: в UI нет функций из раздела 4, `npm run check:ts` и `npm run check:css` проходят.

### Этап 2. Движок Signal и MVP переписки

- `src/lib/signal`: хранилище, сеть, приём с `unprocessed`, отправка (sealed sender, sender keys для групп, retry receipts через `DecryptionErrorMessage`), синхронизация с основным устройством, группы v2 (состояние, изменения, учётные данные zkgroup), профили, вложения (шифрование, загрузка на CDN v3 по TUS, потоковая расшифровка), storage service (чтение и запись архива, закрепа, mute, «непрочитанного», блокировок и принятия запросов).
- `src/api/signal`: `initApi`, `callApi`, `callApiLocal`, методы, которые нужны UI после этапа 1, и маппинг в `ApiChat`, `ApiUser`, `ApiMessage`.
- Экран привязки вместо экранов Telegram. Функции этапа 2 из раздела 3.

Готово, когда: переписка 1:1 и в группе работает в обе стороны с Android, включая вложения, реакции, правки, удаление и исчезающие сообщения, а перезагрузка вкладки не теряет сообщения.

### Этап 3. Удалить GramJS

Удаляем `src/lib/gramjs`, `src/api/gramjs`, конфиг Telegram в `src/config.ts` и `vite.config.ts` (`TELEGRAM_API_ID`, CSP для `*.web.telegram.org`), загрузку langpack, магические id Telegram (`777000` и другие). Строки локализации кладём в сборку.

### Этап 4. Полный функционал связанного устройства

Функции этапа 4 из раздела 3, включая запись в storage service папок, настроек приватности (квитанции, набор, превью ссылок, индикаторы sealed sender, таймер по умолчанию, видимость номера, любимые реакции) и ника с заметкой: в интерфейсе их пока не меняют, поэтому в `storageChanges` таких полей нет.

### Этап 5. Истории

Приём, просмотр, отправка медиа и текстовых историй, списки рассылки, групповые истории, ответы и реакции, квитанции просмотра. Сделано (см. «Ход работ»), кроме превью ссылок в своих историях, перекодирования видео и историй-онбординга; на живом аккаунте не проверено.

### Этап 6. Доводка

Функции этапа 6 из раздела 3, шифрование хранилища код-паролем, PWA, брендинг, документация развёртывания прокси, совместимость с актуальными Signal Android, iOS и Desktop.

### Этап R. Звонки (исследование)

WebRTC браузера не может говорить с RingRTC (факт 5). Остаётся свой медиастек: ICE и SRTP в WASM, кодеки через WebCodecs, UDP через прокси как через TURN (прокси видит только SRTP-шифротекст). Для групповых звонков к этому добавляются протокол SFU Signal и шифрование кадров. Это месяцы работы с неясным исходом, поэтому этап вне основного плана, пока не будет отдельного решения.

## 6. Ограничения

- Пока все вкладки закрыты, сообщения копятся на сервере Signal. Android регистрирует для push токен FCM (`lib/libsignal-service/.../RegistrationApi.kt`); Web Push в API Signal я не нашёл (вывод, код сервера не проверял). Значит, уведомлений при закрытом браузере не будет.
- Очистка данных сайта удаляет ключи и историю, после неё нужна повторная привязка. `navigator.storage.persist()` снижает риск вытеснения, но не защищает от ручной очистки.
- История до привязки доступна только через link-and-sync (этап 4) и только если основное устройство её отправило.
- Превью ссылок не создаются. Desktop и Android скачивают страницу для превью напрямую с сайта (`fetchForLinkPreviews` в `ts/textsecure/WebAPI.preload.ts`, `LinkPreviewRepository` в Android); `contentproxy.signal.org` они используют только для Giphy (`ContentProxySelector.WHITELISTED_DOMAINS` в Android содержит только `giphy.com`). Content proxy слушает порт 443 без TLS (`http://contentproxy.signal.org:443` в `config/default.json` Desktop) и ждёт `CONNECT host:443` открытым текстом, поэтому TLS-рукопожатие через туннель он обрывает, а туннель (`proxy/src/tls.rs`) сам пропускает только ClientHello с SNI разрешённого хоста. Чтобы ходить через content proxy, туннелю нужна политика для открытого `CONNECT` и второй TLS с публичными корнями в WASM (`webpki-root-certs` уже есть в `rust/libsignal/Cargo.lock`, `webpki-roots` нет), но пускает ли content proxy другие сайты, кроме Giphy, проверить не удалось: из этой среды открытый текст до него не проходит (egress отвечает `proxy_ip_not_allowed`). Прямые запросы к сайтам противоречат правилу «только свой origin и туннель».

## 8. Новые зависимости и инструменты

- Крейты libsignal (AGPLv3) в `rust/libsignal/`, rustls для TLS в WASM, wasm-bindgen.
- Инструменты сборки: Rust по `rust-toolchain` libsignal, цель `wasm32-unknown-unknown`, `wasm-bindgen-cli`, `protoc`. Собранный `.wasm` коммитим, чтобы фронтенд собирался без Rust, или собираем в CI.
- npm: `@bufbuild/protobuf` (рантайм), `@bufbuild/protoc-gen-es` и `@bufbuild/buf` (генерация). Хранилище в IndexedDB через `idb-keyval` и прямой API, прокси на `node:http` и `node:net` без зависимостей.

## 9. Принятые решения (2026-11-20)

1. Прокси: P2, туннель без расшифровки TLS.

3. Хранилище: IndexedDB.

6. Название: TeleSignal.
7. Языки: английский и русский.
8. Форк libsignal: в этом репозитории, `rust/libsignal/`.
